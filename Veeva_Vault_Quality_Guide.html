Section 03

Vault Object Model & Relationships

The Object Model is the backbone of Vault. Every quality record — CAPA, Deviation, Audit, Change Control — is an Object. Understanding objects and their relationships is essential for implementation.

3.1 Anatomy of a Vault Object

Every object in Vault has five core components:

📋

Fields

Individual data points — text, dates, lookups, picklists, formulas. Together they make up the "form."

🔄

Lifecycle

The defined states a record passes through — and the transitions between them (with rules and e-sigs).

⚙️

Workflows

Automated task sequences triggered by lifecycle transitions — assignments, notifications, approvals.

🔗

Relationships

How this object connects to other objects or documents — parent/child, lookup, many-to-many.

🛡️

Security

Who can see, edit, or act on this record — controlled by roles, groups, and permission sets.

3.3 Object Relationships — Deep Dive

This is one of the most important and often misunderstood aspects of Vault. Relationships define how records connect to each other and enable traceability across the quality system.

Relationship Type 1: Parent–Child (One-to-Many)

One parent record owns multiple child records. The child cannot exist without the parent. The parent record shows a related list of all its children.

📘 Example

CAPA (Parent) → CAPA Action Items (Children)
One CAPA has multiple action items: "Replace pump seal," "Retrain maintenance staff," "Update PM schedule." Each action item belongs to exactly one CAPA. Deleting the CAPA deletes all its action items.

Parent ObjectChild ObjectRelationship Name
CAPACAPA Action ItemsCAPA to Action Items
AuditAudit FindingsAudit to Findings
Change ControlChange Tasks / ActivitiesChange Control to Tasks
Customer ComplaintComplaint Investigation LinesComplaint to Investigations
Risk AssessmentRisk Line ItemsRisk Assessment to Items

Relationship Type 2: Lookup (Many-to-One)

A record references another record but doesn't "own" it. The referenced record can exist independently. Multiple records can reference the same target.

📘 Example

Deviation → Product (Lookup)
A Deviation references which Product was affected. The Product exists independently in the Product catalog. Many Deviations can reference the same Product. Deleting a Deviation does NOT delete the Product.

Source ObjectLookup TargetField Name
DeviationProductAffected Product
CAPASite / FacilitySite
Change ControlSupplierAffected Supplier
Customer ComplaintCustomer / AccountComplainant
Training AssignmentDocumentTraining Item

Relationship Type 3: Object Reference (Cross-Object Link)

A bidirectional reference between two equal-level objects. Neither owns the other — they simply point to each other, enabling cross-navigation and reporting.

📘 Example

Deviation ↔ CAPA (Cross-Reference)
A Deviation record has a field "Linked CAPA" that points to a CAPA record. The CAPA record has a field "Source Deviation" that points back. You can navigate from either direction. This is the most common relationship type in QMS.

Relationship Type 4: Many-to-Many (Junction Object)

When multiple records of Type A can relate to multiple records of Type B, a "junction object" sits in between.

📘 Example

Employee ↔ Training Curriculum (Many-to-Many)
One employee can be enrolled in many curricula. One curriculum can be assigned to many employees. The "Curriculum Assignment" record is the junction object storing the relationship for each employee-curriculum pair.

3.5 Configuring Object Relationships — Step by Step

Here is how you configure an object relationship in Vault (e.g., linking Deviation to CAPA):

1

Navigate to Business Admin → Objects

Go to the object that will hold the reference field (e.g., Deviation object).

2

Add a new Field → Type: Object Reference

Select field type "Object Reference." This tells Vault this field links to another object.

3

Select the Target Object

Choose "CAPA" as the target object. Optionally filter by lifecycle state (e.g., only show active CAPAs).

4

Set Relationship Type

Reference = peer link (no cascade delete). Parent = child-owns relationship (cascade delete). Choose "Reference" for Deviation→CAPA.

5

Configure Related List on Target Object

On the CAPA object, configure the "Related Objects" section to show all linked Deviations. This creates the bidirectional navigation experience.

6

Set Field-Level Security

Control who can see/edit this relationship field. E.g., only QA roles can link a CAPA to a Deviation.

3.6 Document-to-Object Relationships

Documents (SOPs, reports, evidence files) can be linked to Object records in three ways:

Related Documents SectionThe object record has a "Related Documents" tab showing linked docsChange Control shows all documents being revised
Document BinderGroup related documents into a binder linked to an objectAudit binder contains all audit evidence documents
⚠️ Important: Version Pinning

When a Document Reference field points to a document, it typically links to a specific version. If the SOP is revised, the CAPA still points to the version that was current at the time of the event — preserving the historical record. You can configure whether references auto-update to the latest version or remain pinned.

Section 05

21 CFR Part 11 — Electronic Records & Signatures

The FDA regulation that makes Vault signatures and records legally equivalent to paper. Every pharma professional must understand this deeply.

5.1 What is 21 CFR Part 11?

21 CFR Part 11 is an FDA regulation establishing criteria under which electronic records and electronic signatures are considered trustworthy and equivalent to paper records and handwritten signatures.

  • CFR = Code of Federal Regulations
  • Title 21 = Food and Drugs
  • Part 11 = Electronic Records; Electronic Signatures

5.2 Key Requirements & How Vault Meets Them

RequirementSectionVault Implementation
Validation11.10(a)Veeva validates platform; customers validate their configuration
Audit Trails11.10(e)Auto-generated, immutable, user-independent audit trail on all records
Access Control11.10(d)Unique user IDs, role-based access, automatic session timeout
Authority Checks11.10(g)Only users with correct roles can perform state transitions or sign
Operational Checks11.10(f)Lifecycle enforces valid state sequences; invalid transitions blocked
Training11.10(i)Vault Training module tracks all training on SOPs and system use
Signature Manifestation11.50E-sig block shows: full name, timestamp, meaning (Author/Reviewer/Approver)

5.3 E-Signature in Vault — How It Works

1

User triggers a state transition

E.g., clicking "Approve" on a CAPA or document.

2

Vault prompts for credentials

Username + Password dialog appears. User must re-authenticate.

3

User selects signature meaning

Approved / Reviewed / Authored — configured by admin per transition.

4

Vault records the signature

Full name, title, date/time (UTC), meaning, IP address — permanently in audit trail.

5

Signature block generated

A signature block is appended to the record/document showing all signature data.

The QA team opens Vault, navigates to the document audit trail, and shows: "Sarah Johnson, QA Director — Approved — March 15, 2024, 14:32 EST — Meaning: Approved." The investigator accepts this as 21 CFR Part 11 compliant evidence.

Quality Management System (QMS) — Complete Deep Dive

The most critical section for QMS practitioners and implementers. Covers every QMS process in full detail — from business requirements through configuration, field design, lifecycle, workflow, and real-world implementation — so you can build it from scratch.

7.0 Setting Up Vault QMS from Scratch — Implementation Roadmap

Before building individual processes, you need a solid foundation. This roadmap applies whether you are configuring an existing Vault QMS or building from scratch.

1

Phase 1: Discovery & Requirements (Weeks 1–3)

Interview process owners for each quality process (Deviations, CAPAs, Change Control, etc.). Document current state (paper-based or legacy system). Define future state requirements. Map out all object types needed. Document required fields, lifecycle states, workflows, roles, and integrations. Create a Business Requirements Document (BRD).

2

Phase 2: Master Data Setup (Week 3–4)

Configure master data objects that are referenced by all processes: Product, Site, Supplier, Material, Person/Employee, Department, Equipment. These must exist before any QMS objects are configured, since they are lookup targets. Load master data from source systems (ERP, HR).

3

Phase 3: Picklist Configuration (Week 4)

Build all picklist values before configuring object fields. Key picklists: Severity (Critical/Major/Minor), CAPA Type, Deviation Category, Change Type, Complaint Category, Root Cause Categories, Risk Level, Investigation Phase.

4

Phase 4: Security Model Design (Week 4–5)

Define user groups (QA, Manufacturing, QC, Regulatory, Management). Create Security Profiles for each group. Define permission sets for sensitive fields. Map Application Roles to user types. This is the most critical foundational decision — poor security design is very hard to undo.

5

Phase 5: Object Configuration (Weeks 5–10)

Configure each QMS object one at a time: (a) Create the object, (b) Add all fields, (c) Configure the lifecycle, (d) Build workflows, (e) Configure relationships to other objects, (f) Set up security on each state. Recommended order: Deviation → CAPA → Action Items → Change Control → Complaint → OOS → Audit → Audit Findings.

6

Phase 6: Document Integration (Week 10–11)

Configure QualityDocs-QMS integration. Set up document reference fields on QMS objects. Configure automatic training triggers from QualityDocs to Vault Training. Configure effective date triggers.

7

Phase 7: Reports & Dashboards (Week 11–12)

Build standard QMS reports: Open Events by Type/Site, CAPA Aging, Overdue Events, Training Compliance, Complaint Trends, Change Control Cycle Time. Build Quality KPI dashboards for management review.

8

Phase 8: Validation (Weeks 12–16)

Write and execute IQ/OQ/PQ test scripts. Document all test results. Resolve defects. Get sign-off from QA and business owners. Prepare Validation Summary Report.

9

Phase 9: Training & Go-Live (Week 16–18)

Train all users. Migrate historical records if required. Cut-over from legacy system. Go live. Hypercare support period (2–4 weeks of intensive support post go-live).

🔴 Critical Success Factors

1. Executive Sponsorship: QMS implementation requires cross-departmental buy-in. Without executive support, this fails.
2. Process First, Technology Second: Define and agree on your quality processes on paper before configuring Vault. Trying to design processes inside the tool leads to rework.
3. Incremental Rollout: Go live with one process at a time (e.g., Deviations first) rather than all at once.
4. Change Management: Users resist change. Plan extensive training, job aids, and champions in each department.

7.1 Deviations — Complete Configuration Guide

A deviation is any departure from an approved instruction, procedure, established standard, or specification. It is the most frequently used QMS process and the most common source of CAPAs.

Deviation Types

📋

Planned Deviation

Known in advance. Approved before execution. Example: using alternative equipment because primary is under maintenance. Requires pre-approval.

⚠️

Unplanned Deviation

Unexpected event during manufacturing, testing, or any GxP activity. Initiated as soon as discovered. Most common type.

🔁

Recurring Deviation

The same deviation has been observed before. Flagged automatically in Vault via related records. Mandatory CAPA for recurring events.

Deviation Workflow Configuration

When a deviation moves to "Under Investigation," configure a workflow that:

  • Assigns an investigation task to the QA Investigator with a due date of 5 business days for Critical/Major, 10 business days for Minor
  • Sends email notification to the Investigation Owner, their manager, and the QA Director
  • Sends reminder emails at 50% of due date and 24 hours before due date
  • Escalates to QA Director if overdue by 24 hours

During Batch #2024-0891 filling, an environmental monitor shows a particle count above alert limit. The operator immediately stops the filling line and raises a Deviation in Vault (DEV-2024-0892). Severity: Critical. Immediate actions: Line stopped, environmental re-sampling, batch quarantined. QA assigns investigation to Senior QA Scientist (5-day SLA). Investigation uses 5-Why and Fishbone analysis. Root Cause: HEPA filter integrity failure in filling suite. CAPA initiated (linked CAPA-2024-0234). Regulatory team assesses — not reportable as batch was quarantined before distribution. Batch disposition: Rejected/Destroyed. Deviation closed after CAPA plan approved. Full audit trail preserved for future inspections.

7.2 CAPA — Complete Configuration Guide

CAPA is the backbone of pharmaceutical quality systems. A well-implemented CAPA process demonstrates to regulators that your quality system is self-correcting and continuously improving.

Understanding CAPA vs. Corrective Action vs. Preventive Action

TermDefinitionExample
Corrective Action (CA)Eliminates the cause of a detected nonconformity to prevent recurrenceReplace faulty pump seal that caused out-of-spec fill volume

CAPAThe combined process managing both CA and PAThe Vault record that tracks both the corrective and preventive activities
Immediate/Containment ActionShort-term fix to stop the problem now (NOT a CAPA)Quarantine affected batch while investigation is ongoing

CAPA Workflows — Detailed Configuration

Workflow 1 — Action Plan Approval:
Triggered when CAPA moves to "Action Plan Draft" state. Tasks: QA Reviewer reviews plan (3 days) → QA Director approves with e-signature (2 days). If rejected at any step, returns to CAPA Owner for revision.

Workflow 2 — Implementation Oversight:
After Action Plan Approved. Each Action Item owner receives a task. Weekly digest email to CAPA Owner showing % of action items complete. Escalation email to QA Director if any action item is overdue by 3 days.

Workflow 3 — Effectiveness Check:
Auto-triggered on the Effectiveness Check Date. Assigns task to CAPA Owner to document results. QA reviews effectiveness evidence. If "Not Effective" — CAPA re-opens and a new Action Plan must be created.

⚠️ Common CAPA Implementation Mistakes

1. Confusing containment with CAPA: "We quarantined the batch" is an immediate action, not a corrective action. The corrective action is fixing the root cause.
2. Vague effectiveness criteria: "Monitor the process" is not measurable. Use: "Zero recurrence of this deviation type in the next 6 months of production."
3. Too many action items: CAPAs with 20+ action items are often unmanageable. Focus on root cause. 3–5 focused actions are more effective than 20 vague ones.
4. No re-opening workflow: Build a workflow that re-opens a CAPA if the effectiveness check fails. Many orgs forget this.

📋 Full CAPA Scenario — Batch Record Review Failure

An internal audit finds that batch records are reviewed on average 48 hours after batch completion — significantly above the 24-hour SOP requirement. CAPA-2024-0234 is opened. Source: Audit Finding AF-2024-019.

Root Cause (5-Why): Why late? → No reminder system. Why no reminder? → SOP only specifies timeline, not a notification mechanism. Why no notification mechanism? → Process was designed when volume was low and informal. Why still informal? → No formal escalation defined in management review metrics.

Actions: (1) Configure Vault notification to alert batch record reviewer and supervisor 20 hours after batch completion. (2) Update SOP to specify automatic Vault notification as the review trigger. (3) Add "% batch records reviewed within 24h" as a Quality KPI on the management review dashboard.

Effectiveness Criteria: ≥98% of batch records reviewed within 24 hours for 3 consecutive months post-implementation. Result after 3 months: 99.1%. CAPA closed as Effective.

7.5 OOS / OOT — Configuration Guide

OOS vs. OOT

🔴

Out of Specification (OOS)

Test result falls outside established acceptance criteria. Mandates investigation. Batch cannot be released until resolved. FDA guidance: 2006 OOS Guidance document.

🟡

Out of Trend (OOT)

Result is within spec but trending toward the limit. Early warning signal. Investigate proactively before an OOS occurs. Common in stability studies.

OOS Two-Phase Investigation

1

Phase 1: Lab Investigation (Assignable Cause Search)

Lab checks for analyst error, instrument malfunction, calculation error, sample preparation error. Time limit: typically 5 business days. If assignable cause found (e.g., analyst dropped sample → sample contaminated) → Invalidate the result, re-sample, and retest. Document thoroughly. If no assignable cause found → proceed to Phase 2.

2

Phase 2: Full Investigation

Involves manufacturing, materials, environment. Review: batch manufacturing records, raw material COAs, environmental monitoring data, stability data, equipment calibration/maintenance records. Determine: Is it a lab artifact or a real product failure? If real: batch disposition decision (reject/retest/reprocess). Link to CAPA if required.

⚠️ FDA Expectation

FDA expects that Phase 1 and Phase 2 are clearly documented as separate investigations. You cannot skip Phase 1 and go straight to "it must be a lab error." Vault OOS lifecycle should enforce these two phases as distinct states with mandatory documentation before transition.

Section 10

Advanced Administration

10.1 Lifecycle Configuration Best Practices

  • Never create more states than necessary — each state adds complexity and confusion
  • Always set entry criteria on critical transitions — prevents records moving forward with missing data
  • Use "Allow Cancel" transitions carefully — cancelling a quality record requires documented justification
  • Build "On Hold" states for records waiting on external input (e.g., regulatory response)
  • Test every transition in Sandbox with multiple user roles before UAT

10.2 Workflow Best Practices

  • Assign workflows to Groups, not individual users — groups are easier to maintain as staff changes
  • Always configure due date calculations using business days, not calendar days
  • Build escalation paths for every task — what happens if no one acts?
  • Test with users who have no system knowledge — if they're confused, the workflow needs redesign
  • Keep approval chains short — every extra approver adds days to cycle time

Section 14

Interview Questions & Expert Answers

Commonly asked questions for Vault QMS administrator, consultant, and analyst roles.

Q What is the difference between QualityDocs and QMS in Vault?
A QualityDocs manages controlled documents (SOPs, policies, specifications) through their authoring, review, approval, and lifecycle. QMS manages quality events and processes — deviations, CAPAs, change controls, complaints. They integrate tightly: an effective SOP triggers training assignments, and a CAPA action item can require a document revision, linking both modules in a traceable chain.
Q How does Vault support 21 CFR Part 11 compliance?
A Vault meets Part 11 through: (1) E-signatures requiring username+password re-entry, with name, timestamp, and meaning permanently recorded; (2) Immutable audit trails on all records; (3) Role-based access with unique user IDs; (4) Lifecycle controls enforcing valid state sequences; (5) Authority checks ensuring only authorized users can perform specific actions; (6) System validation by both Veeva and the customer organization per GAMP 5.
Q How would you implement the CAPA process from scratch in Vault?
A I'd start with requirements gathering — interviewing QA to define the CAPA lifecycle, required fields, approval chain, and effectiveness check process. Then configure the CAPA object with all fields (using the appropriate types — formula for Days Open and RPN, object references for source linking), configure the lifecycle states and transitions with entry criteria, build workflows for action plan approval and effectiveness check, configure the Action Items child object with parent-child relationship, set up security profiles for each role, build reports for CAPA aging and compliance, and validate with OQ/PQ test scripts before go-live.
Q What are entry criteria and why are they important?
A Entry criteria are conditions that must be met before a lifecycle state transition is allowed. They're essential for data completeness and GxP compliance — they prevent records from progressing with missing information. For example, a Deviation cannot move from "Under Investigation" to "Root Cause Identified" unless the Root Cause field and Root Cause Detail are populated. This enforces process discipline and prevents shortcuts that would create compliance gaps during inspections.
Q Explain object relationships in Vault and give an example.
A Vault supports three main relationship types. Parent-Child (one-to-many): one CAPA owns multiple Action Items — deleting the CAPA deletes the action items. Lookup (many-to-one): a Deviation references a Product that exists independently — many deviations can point to the same product. Object Reference (peer link): a Deviation references a CAPA and the CAPA references back — neither owns the other. Relationships enable full traceability: from a single Deviation, you can navigate to its CAPA, to each action item, to the evidence documents, and to the training records — all in one click path.
Q What is the difference between a corrective action and a preventive action?
A A corrective action eliminates the cause of a detected nonconformity to prevent recurrence. A preventive action eliminates the cause of a potential problem before it occurs. Example: if a pump seal fails causing OOS fill volumes — replacing the seal is a corrective action (fixes what failed); adding pump wear monitoring to the PM schedule is a preventive action (prevents future failures before they cause OOS). Both are managed in the same CAPA record in Vault, often with separate Action Item records tagged as CA or PA type.
Q How does Vault Training integrate with QualityDocs?
A The integration is event-driven. When a document goes Effective in QualityDocs, Vault checks the training matrix configured for that document type and classification, then auto-creates training assignments for all users in the applicable roles with configured due dates. When a document is revised and a new version goes Effective, new assignments are created for the revised version — the historical training completions on the previous version are preserved. This creates a complete, auditable training record showing every person trained on every version of every document.
