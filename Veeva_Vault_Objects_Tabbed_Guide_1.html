SECTION 1: INTRODUCTION TO VEEVA VAULT

1. Introduction to Veeva Vault

Veeva Vault is a cloud-based content management platform built specifically for the life sciences industry. It is developed by Veeva Systems and is widely used by pharmaceutical, biotechnology, and medical device companies to manage documents, data, and business processes.

1.1 What is Veeva Vault?

Veeva Vault is an enterprise content management (ECM) and data management platform designed for regulated industries. Unlike general-purpose document management systems, Vault combines document management with structured data management through a concept called Vault Objects.

Key Characteristics of Veeva Vault
  • Cloud-native: Fully SaaS, hosted and maintained by Veeva Systems
  • Configured, not customized: Admins configure via UI — no backend code needed
  • Regulation-ready: Built-in audit trails, electronic signatures (21 CFR Part 11), and version control
  • Multi-application: One platform serving Clinical, Regulatory, Quality, Safety, and Commercial
  • Object-driven: Structured data stored in Objects (like database tables with a UI)

SECTION 2: WHAT IS A VAULT OBJECT?

2. What is a Vault Object?

A Vault Object is a structured data entity in Veeva Vault that stores and manages business records. Think of it like a table in a relational database, but with a powerful user interface, relationship capabilities, lifecycle management, security controls, and business logic built in.

Simple Analogy

Imagine a spreadsheet where each row is a record (e.g., a Product, a Study, or a Complaint). Each column is a field. But unlike a spreadsheet, Vault Objects come with workflows, approvals, access controls, lifecycle states, audit trails, and can be linked to documents and other objects. That is a Vault Object.

3.2 Object Naming Convention

API Name Format

Standard Vault Objects: objectname__v (e.g., product__v, study__v, site__v)

Custom Objects: objectname__c (e.g., my_custom_object__c)


__v = Veeva-managed (standard, shipped with the application)

__c = Customer-managed (custom, created by the admin)

Field API Names follow the same pattern: field_name__v or field_name__c

3.3 Object Record Structure

Each record in a Vault Object contains:

  • System Fields (auto-populated by Vault): id, name__v, created_by__v, created_date__v, modified_by__v, modified_date__v, status__v
  • Standard Fields: Fields shipped with the standard object (cannot be deleted, names end in __v)
  • Custom Fields: Fields added by Vault admins (names end in __c)
  • Object Type Field: Determines the record type and drives conditional logic
  • State Field (if lifecycle enabled): Represents the current lifecycle state of the record

Vault uses a layered security model for objects:

  4. Object Type Permissions → restrict access to specific record types
  5. Record-level Sharing → fine-grained access to individual records
SECTION 5: OBJECT TYPES AND THEIR SETTINGS

5. Object Types and Their Settings

Object Types allow a single Vault Object to represent multiple distinct categories of records, each with different fields, layouts, validation rules, and behaviors. This is one of the most powerful features for building flexible data models.

5.1 What is an Object Type?

Object Type is a classification mechanism within a single object. When Object Types are enabled, every record must belong to exactly one Object Type. The Object Type determines:

  • Which fields are visible on that record
  • Which layout is applied to the record
  • Which lifecycle (if any) governs the record
  • Which validation rules apply
  • What actions are available
Real-World Example: Document Request Object

Object Type 1: Label Request → Fields: Label Type, Target Market, Submission Date

Object Type 2: Protocol Amendment → Fields: Amendment Number, Study ID, Reason for Change

Object Type 3: CSR Request → Fields: Study Report Type, Data Cut Date, Author


All three types live in ONE object but behave differently based on Type.

A company has a single "Request" object but needs three distinct workflows: one for Label Requests, one for Protocol Amendments, and one for Regulatory Submissions. How do you handle this?
Enable Object Types on the Request object. Create three Object Types: Label Request, Protocol Amendment, and Regulatory Submission. Assign a different lifecycle to each type. Users select the type on creation, and the system applies the correct fields, layout, and lifecycle automatically.

SECTION 7: OBJECT RELATIONSHIPS — COMPLETE GUIDE

7. Object Relationships in Detail

Object Relationships are the connective tissue of the Vault data model. They define how records in different objects (or the same object) relate to each other, enabling rich data navigation, cascading behaviors, and hierarchical data models.

7.1 Why Relationships Matter

  • Navigate from a Study to all its Sites, and from a Site to all its Adverse Events
  • A CAPA can reference the specific Deviation that triggered it
  • An Audit record can be linked to all the non-conformances identified during that audit
  • Products can be linked to Submissions, which are linked to Countries

7.2 Relationship Types — Overview

Relationship TypeDescription
Lookup RelationshipA soft reference from one object to another. The parent can exist without children. The child can exist without a parent (null allowed)
Master-Detail (Parent) RelationshipA hard parent-child relationship. The child CANNOT exist without the parent. Deleting the parent can cascade-delete children
Many-to-Many (Junction Object)When two objects need a many-to-many relationship, a third "junction" object is created with two parent lookups
Self-Referential (Hierarchical)An object that references itself. Used for hierarchical structures like org charts or nested categories
Document RelationshipLinks a document in the Vault document library to an object record

7.3 Lookup Relationship — Deep Dive

Lookup Relationship Characteristics
  • The child record has a Lookup field storing the parent record's ID
  • Deleting the parent does NOT automatically delete child records
  • The lookup field can be left empty (nullable)
  • On the parent record page, related child records are shown in a "Related Objects" section
  • Admin can configure what fields from the parent are displayed on the child record
  • Can be configured to only look up certain records (using filter criteria)
An Adverse Event record has a Lookup to Study. A user accidentally deletes the Study. What happens to the Adverse Event records?
With a Lookup relationship, the Adverse Event records are NOT deleted. The "Study" lookup field on those records becomes null/blank. The records remain in the system. This is different from Master-Detail where deleting the Study would cascade-delete all child records. If you want to prevent accidental data loss, you can add a Validation Rule that prevents deletion of a Study record if related Adverse Events exist.

7.4 Master-Detail (Parent) Relationship — Deep Dive

Master-Detail Relationship Characteristics
  • The parent lookup field is REQUIRED — cannot be null
  • Deleting the parent can be configured to: Cascade Delete (delete all children) or Restrict Delete (prevent deletion if children exist)
  • The child record inherits some security settings from the parent
  • Enables Rollup Summary fields on the parent (counts, sums of child records)
  • The relationship is enforced at the database level

7.5 Many-to-Many Relationship using Junction Object

How Junction Objects Work — Product <-> Country many-to-many

Step 1: Create a Junction Object: "Product Market"

Step 2: Add Parent Lookup to Product on the Junction Object

Step 3: Add Parent Lookup to Country on the Junction Object


Now: One Product → many Product Market records (one per Country). One Country → many Product Market records (one per Product). The junction object can hold additional fields: Approval Date, Status.

8.5 Layout Best Practices

  • Group related fields in clearly labeled sections (Basic Info, Regulatory Details, Timeline, Audit Info)
  • Put the most important fields in the first section — visible without scrolling
  • Keep required fields prominent — ideally in the top section
  • Use Read-Only for auto-populated system fields so users see them but cannot accidentally change them
  • Create separate layouts for different object types — do not try to put all fields on one layout
  • Use spacers to align fields that should be in the right column
  • Limit related object sections to the most relevant ones — too many sections slow the page
  • Test layouts with different user profiles to verify correct rendering
SECTION 9: VALIDATION RULES

9. Validation Rules

Validation Rules are business logic expressions that enforce data integrity by preventing users from saving a record when certain conditions are met.

Key Concept — Error Condition Logic

IMPORTANT: The expression in a Validation Rule describes the ERROR CONDITION — when the rule returns TRUE, an error is thrown. Think of it as: "Block saving WHEN this condition is true."

9.1 Validation Rule Components

ComponentDescription
NameInternal identifier. Example: "Require_Due_Date_For_Open_CAPAs"
ActiveEnable/disable the rule without deleting it. Useful during data migration or testing
Error Condition FormulaThe expression that, when TRUE, blocks saving
Error MessageThe message shown to the user. Should clearly explain what needs to be corrected
Error LocationPage-level or field-level error. Field-level errors are more user-friendly
Object TypeOptionally restrict the rule to only fire for specific object types

SECTION 10: OBJECT ACTIONS

10. Object Actions

Object Actions are operations that can be performed on Vault Object records. They range from simple navigation actions to complex automated processes triggered by user clicks or system events.

10.1 Types of Object Actions

SECTION 12: VAULT OBJECT BEST PRACTICES

12. Vault Object Best Practices

12.1 Object Design

  • Follow a "one object, one concept" principle — do not overload one object with too many unrelated record types
  • Use Object Types liberally — they are far better than separate objects for closely related data
  • Always design your data model on paper first — draw object relationships before building
  • Name fields consistently across objects (e.g., always use status__v, always use description__c for similar fields)
  • Plan your API naming convention upfront — changing API names later breaks integrations

12.2 Field Design

  • Use Picklists instead of free-text wherever possible — enforces data consistency and enables filtering
  • Avoid over-creating fields — too many fields clutters layouts and slows load times
  • Use Formula fields for derived values — avoids stale data from manually entered calculated fields
  • Use the Description on every field — explains purpose to future admins
  • Create shared picklists (reused across objects) for standard values like Country, Therapeutic Area, Status

12.3 Relationship Design

  • Choose Lookup vs. Parent carefully — use Parent only when true parent-child (child cannot exist without parent)
  • Design junction objects for many-to-many relationships — do not hack it with multi-select picklists
  • Keep relationship chains shallow (max 3-4 levels) — deep chains slow queries and complicate navigation

12.4 Layout & Validation Design

  • Less is more — only show fields that users need on layouts
  • Group fields logically — users scan in reading order (top-left to bottom-right)
  • Write error messages in plain language — tell the user exactly what to fix
  • Deactivate (do not delete) rules during data migration to avoid blocking bulk imports
  • Test rules with positive AND negative test cases before activating
  • Put identification fields (Name, ID, Status, Type) in the first section

SECTION 14: QnA — SCENARIOS AND CONCEPTS

14. QnA — Scenarios and Concepts

What is the difference between a Vault Object and a Vault Document?
A Vault Document is a file (PDF, Word, etc.) managed with version control, electronic signatures, and a document lifecycle. A Vault Object is structured data (like a database record) with fields, relationships, and optionally its own lifecycle. Documents can be linked to Objects but they serve different purposes. Documents are unstructured content; Objects are structured data.
When should you use Object Types vs. creating separate objects?
Use Object Types when records share the same fundamental identity but differ in their fields, processes, or required data. Example: CAPA (Major and Minor) share the same core concept — use Object Types. Create separate objects when the concepts are fundamentally different — a Product and a Study warrant separate objects. Rule of thumb: if it would make sense to report on them together in a list, use Object Types. If they have completely different relationships, lifecycles, and user audiences, create separate objects.
What happens when you delete a Picklist value that is being used by existing records?
Vault prevents the deletion of a picklist value that is actively used on existing records. You must first update all records using that value to a different value before the picklist value can be deleted. Alternatively, you can deactivate the picklist value — deactivated values still appear on existing records but are not available for selection on new or edited records.
Can you change a field type after records have been created?
In Veeva Vault, changing field types is generally not supported after records have been created. The standard approach is to: (1) Create a new field of the desired type, (2) Migrate data from the old field to the new field, (3) Update layouts and validation rules to use the new field, (4) Remove or hide the old field. This is by design to protect data integrity.
What is the difference between a Required field at the Object level vs. Required at the Layout level?
Required at the Object level means the field is mandatory regardless of which layout is being used — the database will always enforce it. Required at the Layout level is a UI-only enforcement that applies only to users using that specific layout. A different layout could make the same field optional. Best practice: use Object-level Required sparingly for truly mandatory fields; use Layout-level Required for contextual requirements.
Explain how a Validation Rule differs from a Required field setting.
A Required field setting simply checks if the field has any value. A Validation Rule is a full formula expression that can enforce complex business logic — for example, "Due Date is required, but only when Status is Open AND Priority is High." Required fields are simple but limited. Validation Rules are powerful and flexible. Validation Rules also fire for API bulk loads.
You need to prevent users from closing a CAPA without entering a Root Cause. How do you implement this?
Create a Validation Rule: Error Condition: ISPICKVAL(status__v, "Closed") AND ISBLANK(root_cause__c). Error Message: "Root Cause Analysis is required before a CAPA can be closed." Additionally, configure the "Close CAPA" lifecycle transition to have Entry Criteria: NOT(ISBLANK(root_cause__c)). Using both provides defense-in-depth.
A pharmaceutical company wants to track Clinical Trial Sites. Each Site can have multiple Site Visits. A Site Visit must always be linked to a Site. When a Site is archived, all its Visits should also be archived. How would you model this?
Create two objects: Site (site__c) and Site Visit (site_visit__c). On the Site Visit object, create a Parent Lookup field pointing to the Site object (making it a master-detail relationship). This ensures: (1) Site Visit cannot exist without a Site, (2) Cascade actions can be configured. For the archiving requirement, create a lifecycle on both objects. On the Site lifecycle, create an Entry Action on the "Archived" state that triggers all related Site Visit records to transition to "Archived" state as well.
Your company needs to track which Countries a Product is registered in, with the registration date and approval status per country. Products can be registered in many countries, and a country can have many registered products. How do you model this?
This is a many-to-many relationship. Create a Junction Object called "Product Registration" (product_registration__c) with: (1) Parent Lookup to Product object, (2) Parent Lookup to Country object, (3) Additional fields: Registration Date (Date), Approval Status (Picklist: Pending, Approved, Rejected), Registration Number (Text), Expiry Date (Date). From the Product record, users can see all countries it is registered in. From the Country record, users can see all registered products.
SECTION 15: INTERVIEW QUESTIONS (100+)

15. Interview Questions — 100+ with Answers

Category A: Fundamentals (Q1–Q20)
Q1. What is a Veeva Vault Object?
A Vault Object is a structured data entity used to store and manage business records in Veeva Vault. It is similar to a database table but includes rich UI, relationship management, lifecycle, security, and business logic. Examples include Product, Study, CAPA, and Site objects.
Q2. What is the difference between a standard object (__v) and a custom object (__c)?
__v objects are Veeva-managed standard objects shipped with Vault applications. They cannot be deleted and have fixed core behaviors. __c objects are created by administrators to meet custom business needs. They can be modified or deleted. The suffix also applies to fields: standard fields end in __v, custom fields end in __c.
Q3. What are the mandatory system fields present on every Vault Object record?
Every Vault Object record has these system fields: id (unique record ID), name__v (the record identifier), status__v (Active/Inactive), created_by__v, created_date__v, modified_by__v, and modified_date__v. These are read-only and auto-populated by Vault.
Q4. What is an Object Type in Vault?
An Object Type is a classification mechanism within a single object that allows different categories of records to have different fields, layouts, lifecycles, and validation rules. For example, a CAPA object can have "Major CAPA" and "Minor CAPA" types — each with a different workflow. Every record of a type-enabled object must belong to exactly one Object Type.
Q5. What is the purpose of the "Prefix" setting on a Vault Object?
The prefix is a short code (3-4 characters) used to auto-generate readable record names when the Name field auto-populate setting is enabled. For example, a prefix of "CAPA" generates names like CAPA-0001, CAPA-0002. It makes records easy to reference and is visible in audit trails.
Q6. Explain the concept of Object Lifecycle in Vault.
A Lifecycle is a state machine attached to a Vault Object that governs the stages a record moves through. It consists of States, Transitions between states, Entry/Exit Actions (automated steps triggered by state changes), and Security (which roles can perform which transitions). Lifecycles enable formal process management and compliance tracking.
Q7. What is the difference between a Lookup field and a Parent Lookup field?
A Lookup field creates a soft (optional) reference to another record. The field can be null, and deleting the referenced record does not delete the record with the lookup. A Parent Lookup creates a hard (required) reference — the parent field cannot be null, and deleting the parent can cascade-delete child records. Parent lookups create master-detail relationships; lookups create simple associations.
Q8. What is a Validation Rule and how does it work in Vault?
A Validation Rule is a formula expression that enforces data integrity. If the expression evaluates to TRUE, the record save is blocked and an error message is shown. The formula describes the error condition — for example, ISBLANK(due_date__c) AND ISPICKVAL(status__v, "Open") blocks saving an Open record without a Due Date.
Q9. What are the components of a Vault Object Layout?
A Vault Object Layout consists of: Field Sections (named groups of fields in a 2-column grid), Fields placed within sections (with optional Required/Read-Only overrides), Spacers for visual alignment, Related Object Sections (showing child records), Related Document Sections (showing linked documents), and overall page structure including the header. Layouts are assigned per Object Type and/or Security Profile.
Q10. What is a Junction Object in Vault?
A Junction Object is a Vault Object used to implement many-to-many relationships between two other objects. It contains Parent Lookup fields to both objects in the relationship, plus any additional fields specific to the relationship itself (e.g., a "Study Investigator" junction object with parent lookups to Study and Investigator, plus fields like Role and Start Date).
Q11. What does "Enable Following" mean on a Vault Object?
"Enable Following" allows users to subscribe to updates on a specific record. When a user "follows" a record, they receive in-app notifications (and optionally email) when the record is updated — field changes, state transitions, or new related records. Useful for stakeholders who need to monitor a record's progress without being directly responsible for it.
Q12. What is a Shared Picklist in Vault?
A Shared Picklist is a set of picklist values defined once at the Vault level and reused across multiple objects and fields. Instead of maintaining the same values (like "Country" or "Therapeutic Area") on every object separately, a Shared Picklist ensures consistency. Updating the Shared Picklist updates all fields that reference it simultaneously.
Q13. How does record-level security work for Vault Objects?
Vault uses a layered security model: Application Roles define broad user capabilities, Object Permissions specify CRUD rights per object per role, Field Permissions control per-field access (read/edit/hidden) per role, Object Type Permissions restrict access to specific record types, and Record Sharing provides granular access to individual records beyond role-based access. The most restrictive permission wins.
Q14. What is the purpose of the Entry Action in a Vault lifecycle?
An Entry Action is an automated action that fires when a record enters a specific lifecycle state without any user interaction. Common entry actions include: Set Field Value (e.g., set approval_date to TODAY() when entering "Approved" state), Send Email notification, Start a Workflow, or Trigger an integration. Entry Actions ensure consistent automation and eliminate the need for users to manually update related fields.
Q15. Can a single Vault Object have multiple lifecycles? How?
Yes. Multiple lifecycles can be assigned to a single object using Object Types. Each Object Type can have its own assigned lifecycle(s). For example, a CAPA object with Object Type "Major CAPA" (complex lifecycle with 6 states) and "Minor CAPA" (simple lifecycle with 3 states). When a new record is created, the Object Type selection determines which lifecycle is applied.
Q16. What is a Formula field and what are its key characteristics?
A Formula field is a read-only field whose value is dynamically computed from an expression. It cannot be manually edited, is always recalculated at display time (not stored), can reference fields on the same object and related objects, and supports functions like TODAY(), IF(), CONCATENATE(), DATEDIF(). Key limitations: cannot be used as parent lookup target, cannot reference other formula fields in circular dependencies, and complex formulas impact page load performance.
Q17. What happens to child records when a parent record is deleted in a Master-Detail relationship?
It depends on the delete behavior configured: Cascade Delete means all child records are automatically deleted when the parent is deleted. Restrict Delete means Vault prevents deleting the parent if any child records exist — the user must first delete or re-parent all children. With a Lookup (non-parent) relationship, deleting the "parent" just nulls out the lookup field on children — they are not deleted.
Q18. What is the difference between Object Actions and Entry Actions?
Object Actions (User Actions) are triggered manually by users clicking a button on a record. They are on-demand and appear in the record's Actions menu. Entry Actions are automated — they fire automatically when a record enters a specific lifecycle state without any user interaction. Entry Actions cannot be "clicked"; they are triggered by the state transition itself.
Q19. How do you prevent a required field from appearing on all object types?
By using the Object Type field configuration. Even though a field exists at the object level, each Object Type can configure the field as Required, Optional, or Hidden (Not Applicable) for records of that type. A field can be Required for Object Type A but Hidden for Object Type B. This is configured in Admin > Objects > [Object] > Object Types > [Type] > Fields.
Q20. What is an Auto-Number field and how does it differ from the Name field auto-populate?
Auto-Number is an explicit field type that generates a sequential formatted number for each record (e.g., "SITE-0001"). It is a separate, dedicated field. Name field auto-populate is a setting on the object that automatically generates the name__v system field using the object prefix plus a sequence. The difference: Auto-Number creates a separate reference field, while Name auto-populate fills the primary identifier field. You can use both simultaneously on the same object.
Category B: Fields and Data Modeling (Q21–Q45)
Q21. What field types are available for storing dates and times in Vault? When would you use each?
Date field: stores only a calendar date (no time). Use for milestones, deadlines, approval dates where time is not meaningful. DateTime field: stores date + time (stored in UTC, displayed in user's timezone). Use for events where exact time matters — adverse event occurrence, approval timestamps for 21 CFR Part 11 compliance, system event logs. Always use DateTime for compliance-critical timestamps.
Q22. What is the difference between a single-select and multi-select picklist?
Single-select picklist: the user can choose exactly one value. Stored as a single text value. Supports ISPICKVAL() in formulas. Multi-select picklist: the user can choose one or more values. Stored as a semicolon-separated string. Does NOT support ISPICKVAL() — use INCLUDES() or CONTAINS() instead. Multi-select picklists are harder to filter and report on, so use them sparingly.
Q23. When would you use a Checkbox field vs. a Yes/No picklist?
Checkbox: always has a value (true or false — never null). Use when you need a definitive true/false state, such as "Is GCP Compliant?" or "Training Complete?" Yes/No Picklist: can be null (no value selected). Use when "not yet answered" is a meaningful state — for example, "Has the IRB approved this study?" where null means "unknown". A null checkbox defaults to false, which may be misleading in some scenarios.
Q24. What is a dependent picklist? How do you configure it in Vault?
A dependent picklist filters the available values based on the selection in a controlling field. Example: Country (controlling) determines which Region values appear. Configuration: (1) Create both picklist fields, (2) On the dependent field, define a "controlling field," (3) Map which dependent values should appear for each controlling value. This reduces user error by only showing relevant choices.
Q25. What are the limitations of Text fields in Vault?
Text fields: maximum 1,500 characters. Single line only (no line breaks). Cannot store HTML by default. Text fields are indexed and searchable. Long Text fields (up to 32,000 chars) are not indexed for full-text search in the same way. Text fields cannot store binary data or attachments. For large text content, use Long Text fields or Vault documents.
Q26. Explain how a Lookup field filter works.
A Lookup field filter restricts which records are available for selection when a user opens the lookup picker. Example: a "Product" lookup filtered to only show records where status__v = "Active" ensures users can only link active products. Filters use field comparison expressions. Dynamic filter values referencing current user or current record are particularly powerful for context-aware lookups.
Q27. What is the Object Reference field type?
An Object Reference field is a polymorphic lookup that can reference records from multiple different objects. Unlike a regular Lookup (which targets one specific object), an Object Reference field can point to a Product, Study, or Site depending on context. The stored value is a combination of the object API name and the record ID. Useful for generic "parent entity" fields in utility objects like Tasks or Notifications.
Q28. How would you design a field to store a calculated "Days Open" value for a CAPA record?
Use a Formula field with a Number return type. Formula: TODAY() - created_date__v. For closed CAPAs, use: IF(ISPICKVAL(status__v, "Closed"), closed_date__c - created_date__v, TODAY() - created_date__v). This prevents the counter from growing indefinitely after closure and shows the actual duration the CAPA was open.
Q29. What is the "Unique" field setting? What happens when you enable it?
The Unique setting enforces that no two records in the same object can have the same value in that field. If a user tries to save a record with a value that already exists, Vault blocks the save with an error. Use for fields that should be globally unique identifiers, like Study Protocol Numbers, Product Codes, or CAPA reference numbers. Note: Unique is case-insensitive by default.
Q30. Can you change the API name of a field after it has been created?
Yes, technically you can change the API name in Vault configuration. However, this is extremely risky in a live system because any integrations, formulas, VQL queries, and validation rules that reference the old API name will break immediately. Best practice is to treat API names as permanent once established. If you must rename, only do so in a development sandbox and update ALL references before deploying to production.
Q31. What formula functions can you use in Vault Validation Rules?
Key functions: ISBLANK() — checks if field is empty, ISPICKVAL() — checks picklist value, AND()/OR()/NOT() — logical operators, LEN() — string length, TODAY()/NOW() — current date/time, CONTAINS() — substring check, REGEX() — pattern matching, IF() — conditional, INCLUDES() — for multi-select picklists, VALUE() — converts text to number, TEXT() — converts to text, DATEVALUE() — date conversion, YEAR()/MONTH()/DAY() — date components.
Q32. How do you make a field read-only for one Object Type but editable for another?
At the Object Type level, configure the field's behavior: set it to "Read Only" for Type A and "Editable" for Type B. This is done in Admin > Objects > [Object] > Object Types > [Type] > Fields. You can also achieve this via Layout configuration by placing the field in read-only mode in the layout assigned to Type A, while leaving it editable in the layout for Type B. Layout-level read-only is UI-only; object-type-level configuration is more robust.
Q33. What is a User field in Vault? How is it different from a Text field storing a username?
A User field is a Lookup field specifically referencing the User object. It stores the actual User record ID and displays the user's full name as a clickable link to their user profile. It supports dynamic default values like "Current User." A Text field storing a username is just plain text — no validation, no link, no dynamic default, and no integration with Vault's user management.
Q34. Explain the Help Text field setting. When and how should you use it?
Help Text is a short description that appears as a tooltip (?) icon next to a field label when users hover over it. Use it for: fields whose labels alone are ambiguous, fields with specific formatting requirements, and fields used in regulated processes where incorrect data entry has compliance implications. Keep help text concise — 1-3 sentences maximum.
Q35. What is the default value setting on a field? What types can have defaults?
The Default Value setting pre-populates a field when a new record is created. Available for: Text (static text), Number (static number), Date (TODAY() or specific date), DateTime (NOW() or static), Picklist (a specific value), Checkbox (true or false), User fields (Current User). Defaults reduce data entry errors and speed up record creation. Users can override defaults unless the field is Read-Only.
Q36. How do you query Vault Objects using the API?
Use VQL (Vault Query Language) via the Vault REST API. Example: GET /api/v24.0/query?q=SELECT id, name__v, status__v FROM product__v WHERE status__v = "Active". VQL supports SELECT, FROM, WHERE, ORDER BY, LIMIT, OFFSET. You can traverse relationships using the relationship API name: SELECT id, name__v, product__vr.name__v FROM study__v.
Q37. What is field-level security in Vault Objects?
Field-level security (FLS) controls whether a specific field is readable, editable, or completely hidden for users in a specific security profile or role. Configuration: Admin > Security > [Profile] > Object Permissions > [Object] > Field Permissions. Settings per field: Read (see value, cannot edit), Edit (see and change value), Hidden (field is completely invisible). FLS applies everywhere: record pages, reports, search results, and API responses.
Q38. Can you have a required field that has no validation rule?
Yes. Marking a field as Required at the object level is a separate mechanism from Validation Rules. A Required field uses built-in Vault enforcement — no formula needed. Vault automatically rejects saves if the field is empty. Validation Rules are additive — they add MORE complex logic on top of simple required enforcement. Both can and do coexist.
Q39. What are the audit trail capabilities for Vault Object fields?
Vault automatically logs: record creation (all field values), field value changes (old value, new value, who changed it, when), lifecycle state transitions, record deletion, and sharing changes. The audit trail is accessible from the record's "History" tab and via the API. The audit trail is tamper-proof and meets 21 CFR Part 11 requirements for electronic record integrity.
Q40. What is the maximum character limit for a Long Text field in Vault?
32,000 characters (approximately 32KB of text). This is sufficient for most narrative fields like descriptions, findings, and analysis. For extremely long content, Vault documents (PDF, Word) should be used instead. Long Text fields are rendered as multi-line text areas in the UI.
Q41. Explain the CONTAINS() vs. INCLUDES() formula functions.
CONTAINS(text, "substring") is used with Text fields to check if the text value contains a specific substring. Example: CONTAINS(product_name__c, "Generic"). INCLUDES(multiselect_field, "value") is specifically for Multi-Select Picklist fields — it checks if any of the selected values equals the specified value. Never use ISPICKVAL() with multi-select picklists — it will not work correctly.
Q42. How would you track the history of value changes for a specific field?
Vault's built-in Audit Trail tracks all field value changes automatically. To view: open the record, click the History/Audit Trail tab. Each entry shows: field name, old value, new value, user who made the change, timestamp. For API access: GET /api/v24.0/vobjects/[object]/{record_id}/audittrail. If you need cross-record change reporting, query the audit trail API and aggregate the results.
Q43. Can a Formula field reference fields from related objects (via lookup)?
Yes, Formula fields can reference fields on related objects through lookups using the relationship API name with the __vr or __cr suffix. Example: on a Study record, a formula can reference study_site__vr.site__vr.country__c to get the country of the related site. However, traversal depth is limited (typically 1-2 levels in formulas) and performance degrades with deep traversals.
Q44. What is a controlled picklist in the context of Vault Objects?
A controlling picklist is a picklist field that drives the available values in another dependent picklist. Example: "Submission Type" (controlling) with values IND, NDA, BLA determines which "Submission Sub-Type" values are available. If Submission Type is IND, Sub-Type shows: Phase I, Phase II, Phase III. If NDA, Sub-Type shows: Standard, Priority, Accelerated. Implemented through the dependent picklist's controlling field configuration.
Q45. What is the difference between saving a field as Active vs. Inactive in Vault?
There is no Active/Inactive status on fields themselves. Fields either exist and appear on layouts, or they are hidden/removed from layouts. However, at the Picklist value level, values can be Active or Inactive — inactive picklist values no longer appear in the dropdown for new records but still display on existing records that use that value. At the Object level, Object Types can be Active or Inactive.
Category C: Relationships and Data Model (Q46–Q65)
Q46. How many levels deep can you traverse in a Vault Object relationship query?
In VQL queries, you can traverse relationships multiple levels deep. The practical limit is typically 5-10 levels, but performance degrades with depth. In formulas, traversal is more limited — typically 1-2 levels. For complex deep traversals, it is better to denormalize frequently accessed values (store them on the child record via formula or entry action) rather than traverse deep hierarchies in every query.
Q47. What is the difference between a Relationship Name and a Relationship Label in Vault?
The Relationship Name is the API name used in VQL queries to traverse the relationship. For example, studies__vr is used in: SELECT id, studies__vr.name__v FROM product__v. The Relationship Label is the display name shown to users in the UI for the related object section on the parent record. Example: the label "Clinical Studies" appears as the section header on the Product record for related Study records.
Q48. Can a child object have multiple parent lookups to different objects?
Yes. A child object can have multiple lookup (or parent lookup) fields pointing to different parent objects. Example: a CAPA record can have a lookup to Site (where the issue occurred) and a separate lookup to Product (which product was affected). These are independent relationships, each traversed separately.
Q49. What is a self-referential relationship? Give an example.
A self-referential relationship is when an object has a lookup field pointing to the same object type. This creates a hierarchical (tree) structure. Example: an Organization object where each record has a "Parent Organization" lookup to the same Organization object, creating: HQ → Division → Department → Team. Another example: a Product Category object where categories can be nested.
Q50. How would you model a Study that can have multiple Countries, and each Country can have multiple Studies?
Use a Junction Object. Create: (1) Study object, (2) Country object, (3) Study Country (junction object) with Parent Lookup to Study and Parent Lookup to Country, plus additional fields like "Submission Date" and "Regulatory Status." From the Study record, users see all countries in the Study Country related section. From the Country record, users see all related Studies.
Q51. What happens to a Lookup field value when the referenced record is deleted?
With a standard Lookup (not a Parent Lookup), if the referenced record is deleted, the lookup field value on the child record is set to null/blank. The child record is NOT deleted — it simply loses its reference to the deleted parent. This can leave orphaned records. With a Parent Lookup (master-detail), the admin configures the behavior: Restrict Delete or Cascade Delete.
Q52. When should you use a junction object vs. a multi-select picklist for a many-to-many relationship?
Use a Junction Object when: the relationship itself has additional data, when you need to navigate FROM both sides, when compliance requires auditability of each individual relationship, or when the number of related items can be very large. Use a Multi-Select Picklist when: the relationship is simple (no extra data), the list of options is short and stable, and you do not need to navigate from the "other side." Multi-select picklists are not true relationships and should be used sparingly.
Q53. What is the significance of the "Delete Behavior" setting on a Parent Lookup?
Delete Behavior determines what happens to child records when the parent is deleted. Cascade Delete: all child records are automatically and immediately deleted — irreversible and potentially dangerous for compliance data. Restrict Delete: Vault prevents deleting the parent record if ANY child records exist. In regulated industries, Restrict Delete is strongly preferred to prevent accidental data loss in audit-critical records.
Q54. How can you link a Vault Document to an Object Record?
Several methods: (1) The document can have a lookup field to the object — the object record's related documents section automatically shows the linked document. (2) Use "Relate Document" action on the object record to manually link any document. (3) Standard objects like Study and Site have dedicated document relationship sub-objects. (4) Via Vault API, create a document relationship object record linking the document ID to the object record ID.
Q55. What is the relationship between a Lifecycle and an Object Type?
Object Types and Lifecycles work together. A single object can have multiple lifecycles (one per Object Type). When creating a record, the selected Object Type determines which lifecycle(s) are available and which one is the default. Different Object Types can have entirely different lifecycles — Major CAPA might have 6 states with formal approvals, while Minor CAPA might have 3 states.
Q56. How do you retrieve all child records for a parent using the Vault API?
Use VQL with a subquery or direct query: Method 1 - Subquery: SELECT id, name__v, (SELECT id, name__v FROM sites__vr) FROM study__v WHERE id = "V1000000001". Method 2 - Direct query: SELECT id, name__v, study__vr.name__v FROM site__v WHERE study__v = "V1000000001". Method 3 - REST API: GET /api/v24.0/vobjects/site__v?q=study__v="V1000000001".
Q57. What is a Document Relationship Object in Vault?
Certain standard Vault objects have a built-in Document Relationship Object — a system-created sub-object specifically designed to link documents to the parent object record. It stores: the document ID, document version, link type, and optionally custom fields. Example: the Study object has a Study Document Relationship object that links TMF documents to the study with additional metadata about the document's role.
Q58. What is the difference between deleting a record and making it "Inactive" in Vault?
Deleting a record: permanently removes it from the system. Destructive and irreversible. Making Inactive: sets the status__v field to "Inactive." The record still exists, is still in the audit trail, but is excluded from default list views and lookup search results. Inactive is the preferred approach for regulatory data — it preserves the record for audit purposes while removing it from active use.
Q59. How would you design an object model for a Quality Management System covering CAPAs, Deviations, and Change Controls?
Core Objects: (1) Deviation — records of non-conformances. (2) CAPA — corrective/preventive actions with a Lookup to Deviation. (3) Change Control — controlled changes with a Lookup to CAPA. Supporting Objects: Site, Product, User (for assignments). Each has its own lifecycle and Object Types for severity classification. Junction objects link products and sites to each quality record. Layouts are configured per Object Type and role.
Q60. What is VQL and how is it used to query Vault Objects?
VQL (Vault Query Language) is Vault's SQL-like query language used to retrieve object records via the REST API. Syntax: SELECT field1, field2 FROM object_name WHERE condition ORDER BY field LIMIT n. Features: relationship traversal (product__vr.name__v), subqueries for child records, aggregate functions (COUNT), FIND() for full-text search. Used by integrations, reports, and Vault Loader.
Q61. What is the Vault Loader and how is it used with Objects?
Vault Loader is a desktop application provided by Veeva for bulk import/export/update/delete of Vault Object records using CSV files and the Vault REST API. Operations: Extract (export records to CSV), Load (import records from CSV), Update (update existing records), Upsert (insert or update based on unique field), Delete. Vault Loader respects all Vault security, validation rules, and lifecycle constraints.
Q62. What are Lifecycle Roles and how do they differ from Application Roles?
Application Roles: broad permissions assigned to users globally across the Vault application. Lifecycle Roles: specific roles assigned to particular records that grant additional permissions on just those records. Example: on a specific CAPA record, User A is assigned the "CAPA Owner" lifecycle role — this grants User A special permissions on ONLY that CAPA, not all CAPAs. Lifecycle Roles enable record-specific access control beyond blanket role-based security.
Q63. What is the importance of the "Status" field (status__v) on Vault Objects?
The status__v field is a system-managed picklist field on every object with two standard values: Active and Inactive. Active records appear in default list views and lookup searches. Inactive records are hidden from default searches and lookup pickers — effectively "archived" without deletion. Inactive records are still accessible via explicit queries and preserved for audit purposes. IMPORTANT: status__v is separate from lifecycle states.
Q64. What are the GxP implications of the Vault Object audit trail?
21 CFR Part 11 (FDA) and EMA Annex 11 require that electronic records be accurate, trustworthy, and audit-trailed. Vault's object audit trail: (1) Is tamper-proof and cannot be modified or deleted by any user, (2) Records every create, update, delete with timestamp and user identity, (3) Maintains old and new values for field changes, (4) Is linked to user authentication, (5) Can be exported for regulatory inspection. This makes Vault Object records suitable for GxP-regulated data.
Q65. Describe the process of migrating object data from one Vault to another.
Process: (1) Prepare a migration plan — map source fields to target fields, identify relationship dependencies. (2) Export data from source using Vault Loader or VQL API. (3) Handle relationships — parent records must be loaded before children. Maintain ID mapping (source ID → target ID) for lookup fields. (4) In target Vault, deactivate relevant Validation Rules. (5) Use Vault Loader or API to load records in dependency order. (6) Re-enable Validation Rules. (7) Validate: run count checks, spot-check records, verify relationships.
Category D: Layouts, Validation, and Actions (Q66–Q80)
Q66. How many layouts can you create for a single Vault Object?
You can create multiple layouts for a single object. The practical maximum is determined by the number of Object Type + Security Profile combinations, as each combination can have a distinct layout. If an object has 5 Object Types and 4 Security Profiles, you could potentially have 20 different layout assignments. There is no hard-coded limit on the number of layouts per object.
Q67. What is a "Spacer" in a Vault layout, and why would you use it?
A Spacer is a blank placeholder in the 2-column layout grid. Since fields are placed in left-right pairs, a Spacer fills one slot when you want a field to appear in a specific column position without a corresponding field on the other side. Example: if you want a field to appear in the RIGHT column only, place a Spacer in the left column and the field in the right. This gives admins fine-grained control over visual alignment.
Q68. What is the difference between making a field Required at the layout level vs. using a Validation Rule?
Layout-level Required: enforced by the UI rendering — users see the asterisk (*) marking. Works only when using that specific layout. A user using a different layout or API might bypass it. Validation Rule Required: enforced at the data layer regardless of layout or API calls. More robust. Validation Rules also fire for API bulk loads. Best practice: use both for critical fields — layout-level for UX clarity, validation rule for data integrity enforcement.
Q69. Explain the concept of "Entry Criteria" on a lifecycle transition.
Entry Criteria is a formula-based condition that must evaluate to TRUE before a lifecycle transition can be executed. If the criteria is not met, the transition button is either hidden or disabled. Example: transition "Close CAPA" has Entry Criteria: NOT(ISBLANK(root_cause__c)) AND NOT(ISBLANK(corrective_action__c)). The CAPA cannot be closed until both fields are filled. Entry Criteria gates progression, complementing (but not replacing) Validation Rules.
Q70. What is a "User Action" in a Vault lifecycle and how is it different from a state transition?
A User Action is a button on a record that users click manually while the record is in a specific state. Unlike a state transition (which moves the record to a new state), a User Action does NOT change the lifecycle state. It triggers an operation while keeping the record in its current state. Examples: "Send Reminder Email" button on a CAPA In Review — sends an email without moving the record. "Generate Report" button — creates a document.
Q71. How do you configure an action to send an email notification when a lifecycle state changes?
Add an Entry Action on the target lifecycle state. Set the Action Type to "Send Email." Configure: Email Template (a pre-defined Vault email template), Recipients (role-based, specific users, or email field values on the record), Sender (typically a system email or admin address). The email fires automatically when the record enters that state. For multi-recipient emails, use role-based recipient configuration.
Q72. What happens if two validation rules conflict?
Both rules fire independently. If Rule A says ISBLANK(field__c) is an error (field must be filled) and Rule B says NOT(ISBLANK(field__c)) is an error (field must be empty), then the record can never be saved — both rules will always fire. This is a configuration error. Admins must ensure validation rules are designed without logical contradictions by accounting for Object Types, record states, and conditions.
Q73. Can you suppress a validation rule for specific users or roles?
Vault validation rules do not have a native "bypass for role" setting. Indirect approaches: (1) Include a condition in the validation rule formula checking user role. (2) Use a special lifecycle state or object type that has a different set of active validation rules. (3) Deactivate the rule during administrative operations. For most compliance use cases, validation rules should NOT be bypassable by any user role.
Q74. Describe the layout assignment logic when both Object Type and Security Profile assignments exist.
Vault evaluates layout assignment using a priority cascade: First, look for a layout assigned to the exact combination of [current Object Type + current User Profile]. Second, look for a layout assigned to [current Object Type + default profile]. Third, look for [default type + current User Profile]. Fourth, use the Default layout. This cascade allows maximum flexibility — you can have profile-specific layouts for some types and shared layouts for others.
Q75. How would you prevent users from deleting records that are in "Approved" lifecycle state?
Configure security on the object lifecycle. In the lifecycle state "Approved," remove Delete permission from all roles. Additionally, in the Object Type security settings, restrict Delete action to only be available in specific states (typically Draft or Cancelled). The recommended approach is lifecycle-based security + object-level role permissions — this is more robust than attempting to use validation rules for deletion control.
Q76. What is the "Confirmation Required" setting on an action?
"Confirmation Required" displays a confirmation dialog box when a user clicks an action button. The dialog shows a configurable message with OK and Cancel buttons. If the user clicks OK, the action proceeds; if Cancel, nothing happens. Use this for: irreversible state transitions (Approve, Cancel, Delete), actions that trigger external notifications or integrations, and high-stakes operations where accidental clicks could cause problems.
Q77. What is the "Active" checkbox on a Validation Rule? When would you deactivate a rule?
The Active checkbox controls whether a Validation Rule is currently enforced. When deactivated, the rule exists but does not fire. Deactivate (do not delete) rules when: (1) Performing bulk data migrations where valid historical data might not meet current rules, (2) Troubleshooting — deactivating a rule lets you test if it is causing unexpected blocks, (3) During a system upgrade or data correction project. Always reactivate rules after the exceptional operation and document the action.
Q78. How would you implement a "four-eyes" approval process in Vault Objects?
Implementation: (1) Create two User fields: "First Approver" and "Second Approver". (2) Configure lifecycle with states: Pending First Approval → First Approved → Pending Second Approval → Fully Approved. (3) Configure transitions: "First Approve" only available to users who match the First Approver user field (using lifecycle role assignment). (4) Entry Action on "First Approved" state notifies the Second Approver. (5) "Second Approve" transition only available to the Second Approver user. (6) Validation Rule: ensure First and Second Approvers are different users.
Q79. A Validation Rule is blocking a critical data correction. What are your options?
Options: (1) Deactivate the Validation Rule, make the correction, reactivate. Document the exception. (2) Temporarily modify the Validation Rule formula to include an exception condition — use cautiously, revert immediately. (3) Change the record's lifecycle state to one where the rule does not apply (if the rule is state-conditional). Always document exceptions for GxP audit purposes in a change control record.
Q80. How would you approach a Vault Object configuration review for a new Vault implementation?
Step 1: Requirements Gathering — document all business processes, data entities, users, and integration needs. Step 2: Data Model Design — identify objects, fields, relationships on paper before building. Step 3: Review against Vault best practices. Step 4: Security Review — define all roles, permissions, field-level security. Step 5: Lifecycle Design. Step 6: Layout Design — create wireframes. Step 7: Validation Rule Review. Step 8: UAT — end-user testing with all profiles. Step 9: Performance Testing. Step 10: Documentation before go-live.
Category E: Advanced and Scenario-Based (Q81–Q102)
Q81. How does Vault handle concurrent record edits?
Vault uses optimistic locking. Each record has a modified_date__v timestamp. When a user opens a record for editing, Vault notes the current timestamp. When the user saves, Vault checks if the timestamp matches. If another user saved in the meantime, the second user's save fails with a conflict error: "This record has been modified by another user. Please refresh and reapply your changes." This prevents data overwrites.
Q82. What is the Vault API session ID and how is it obtained?
The session ID is an authentication token required for all Vault API requests. Obtain it via: POST /api/v24.0/auth with body username={user}&password={pass}&vaultDNS={vault_DNS}. The response includes the sessionId. Include in all subsequent API requests as a header: Authorization: {sessionId}. Session IDs expire after a period of inactivity (typically 30-60 minutes). For service-to-service integrations, use Vault's OAuth or integration user accounts.
Q83. How do you handle historical data that does not conform to newly added Validation Rules?
Best approach: (1) Add the new Validation Rule in INACTIVE state first. (2) Query all existing records that would violate the rule. (3) Create a data remediation plan — either clean the data or accept it as historical. (4) For historical data that legitimately cannot be corrected, consider making the rule conditional on a date: AND created_date__v >= 2024-01-01. (5) Activate the rule after remediating non-compliant data. (6) Document the decision in a change control record.
Q84. How do you handle errors during a Vault Loader bulk import?
Vault Loader error handling: (1) Failed records are written to an error CSV file with the error message for each record. (2) Review error CSV — common errors: validation rule failures, required field violations, duplicate unique field values, invalid lookup references. (3) Fix the source data and re-load only the failed records. (4) For large loads, use the --idparam flag to upsert to avoid duplicates on re-runs. Best practice: always test with a small batch first (10-20 records), check results, then proceed with full load.
Q85. What is the difference between Object-level delete permission and lifecycle-state-level delete permission?
Object-level Delete permission: controls whether a user's role can delete any record of this object, regardless of state. Lifecycle-state-level: even if a role has Object-level Delete, lifecycle state security can block deletion in specific states. Example: QA Analyst role has Object-level Delete permission but the lifecycle security for the "Approved" state removes Delete for QA Analyst. Result: QA Analysts can delete Draft records but not Approved records. Both layers must allow deletion for a delete to succeed.
Q86. How do you create a Vault Object record via the REST API?
POST to /api/v24.0/vobjects/{object_name}. Request body: JSON with field name-value pairs. Example: POST /api/v24.0/vobjects/product__v with body {"name__v": "Aspirin 100mg", "therapeutic_area__c": "Cardiology", "status__v": "Active"}. Authentication: include session ID in header (Authorization: {session_id}). Response: the new record ID and status. The API respects all security settings, validation rules, and required fields.
Q87. How would you design a Vault Object model for tracking regulatory submissions across multiple countries?
Objects: Product (what is being submitted), Country (markets), Submission (the actual regulatory submission), Health Authority (the regulator). Relationships: Submission → Product (lookup), Submission → Country (lookup), Submission → Health Authority (lookup). Object Types on Submission: Initial Application, Variation, Renewal, Annual Update. Lifecycle: Planned → Under Preparation → Submitted → Under Agency Review → Approved/Rejected. Additional child objects: Submission Dossier, Submission Correspondence, Approval Condition.
Q88. How would you manage a situation where an object was misconfigured in production?
Process: (1) Assess impact — how many records are affected? (2) Raise a Change Control record documenting the issue and proposed fix. (3) Test the fix in UAT/development Vault. (4) Schedule a change window. (5) For field changes: cannot change field type, but can add a new field and migrate data. (6) For layout changes: safe to change anytime. (7) For validation rule changes: deactivate old rule, add new rule. (8) Document all changes in the audit trail. (9) Communicate to affected users.
Q89. Describe how you would set up a Vault Object to support a clinical trial master file (TMF) structure.
TMF structure: Study (top-level object), Zone object (TMF Zone: Trial Management, Central Trial Documents, etc.) linked to Study, Section object linked to Zone, Artifact object (the TMF artifact type) linked to Section, Study Country and Study Site linked to Study. Documents are linked to Study, Site, or Country records via document lookup fields. TMF Reference Model artifacts are defined as Object Types on the Artifact object. Lifecycle on artifacts tracks completeness. Reports give TMF completeness percentage per study.
Q90. How would you implement a notification system to alert users when a CAPA due date is approaching?
Several approaches: (1) Date-based notification: Configure a scheduled automation that triggers an email/notification when due_date__c is X days from NOW(). (2) Lifecycle User Action with Entry Criteria: expose a "Send Reminder" button only when due_date__c is within 7 days. (3) Create an "Overdue" lifecycle state with an Entry Action sending notifications, triggered by an external scheduler. (4) External integration: a middleware system queries Vault daily via API for approaching due dates and sends notifications.
Q91. How would you troubleshoot a record that cannot be saved despite all required fields being filled?
Troubleshooting steps: (1) Check Validation Rules — look at all active rules for the object and Object Type. Read the error message carefully. (2) Check formula errors — a formula in a validation rule might throw an unexpected error if a referenced field is null. (3) Check Unique field violations — unique fields block save if another record has the same value. (4) Check field permissions — is the user editing a read-only field? (5) Check lifecycle state — is the record in a state that prevents editing? (6) Use a System Admin account to test — if admin can save but user cannot, the issue is permissions.
Q92. What is Vault's approach to data archiving for Object records?
Vault's primary archiving mechanism is the status__v field (Active/Inactive). Set records to Inactive to archive them — they disappear from active use but remain fully accessible and auditable. Physical deletion of records is generally discouraged in regulated environments — companies maintain records per their retention schedules (FDA requires 2-15+ years depending on record type). Vault's audit trail persists even after record inactivation.
Q93. How do you configure the Vault Object to send a notification when the record status changes to "Overdue"?
Create an "Overdue" lifecycle state. Configure an Entry Action on the Overdue state: Action Type = Send Email. Template = Overdue Notification Template (referencing merge fields from the object). Recipients = owner__v (the record owner) + QA Manager lifecycle role. To move records to Overdue state automatically, use a time-based entry action or external integration (Vault may not natively support scheduled state transitions in all versions — this may require an external scheduler calling the API).
Q94. What is the Vault Object Permissions model? List all permission levels.
Vault Object Permissions are set per Role per Object. Permission levels: (1) CRUD permissions: Create, Read, Edit, Delete. (2) Field Permissions (per field, per role): Read, Edit, Hidden. (3) Object Type Permissions: which Object Types are accessible to this role. (4) Lifecycle Permissions: which state transitions can this role perform. (5) Action Permissions: which Actions are available to this role. All must be configured for complete access control.
Q95. Can two objects reference each other in a circular relationship? What are the implications?
Technically, it is possible to have Object A with a lookup to Object B and Object B with a lookup to Object A (bidirectional). However, this creates a circular dependency that can cause issues with cascade deletes, formula evaluation, and data integrity. Vault allows creating such relationships but admins should carefully consider whether they are truly needed. It is usually better to redesign the data model to avoid circular references, perhaps using a third mediating object.
Q96. What is the difference between a Rollup Summary field and a Formula field?
A Rollup Summary field aggregates values from CHILD records (COUNT, SUM, MIN, MAX of a child field) and stores the result on the PARENT record. It operates across a relationship. A Formula field computes a value from fields on the SAME record (or referenced parent records via lookup traversal). It does not aggregate across multiple child records. Vault has limited native rollup support; complex rollups typically require entry actions or integrations to update a field on the parent.
Q97. How does Vault enforce 21 CFR Part 11 compliance through Object configurations?
Key mechanisms: (1) Audit Trail — tamper-proof log of all record changes with user identity and timestamp. (2) Electronic Signatures — lifecycle transitions can require electronic signatures (password re-entry). (3) DateTime fields for approval timestamps (not just Date). (4) User fields for approval-by tracking (linked to authenticated user accounts). (5) Lifecycle state security — only authorized roles can approve. (6) Validation Rules — enforce data completeness before state transitions. (7) Vault's access control ensures only authenticated, authorized users can make changes.
Q98. What is the purpose of the Object Type Group setting?
Object Type Group is a purely organizational setting that groups related Object Types together in the admin interface for easier management. It has no impact on the behavior of records, security, lifecycles, or layouts. It is useful when an object has many Object Types (e.g., 20+ types) and you want to group them into logical categories (e.g., "Clinical Types," "Regulatory Types," "Quality Types") for administrative clarity. End users do not see the grouping.
Q99. How would you test a newly configured Vault Object before deploying to production?
Testing approach: (1) Create test records for each Object Type. (2) Test all required field validations — try to save without required fields. (3) Test all Validation Rules — both positive cases (should pass) and negative cases (should fail with correct error message). (4) Test lifecycle transitions — try to transition with and without meeting entry criteria. (5) Test each layout with each relevant security profile. (6) Test relationships — create child records, test delete behavior. (7) Test API operations via Postman or scripts. (8) Perform User Acceptance Testing (UAT) with actual business users. (9) Document all test results.
Q100. Explain how you would design a Vault Object for tracking Adverse Events in a pharmacovigilance system.
Object: Adverse Event (adverse_event__c). Object Types: Serious Adverse Event (SAE), Non-Serious Adverse Event (non-SAE), Adverse Drug Reaction (ADR). Key Fields: Patient ID (Text), Onset Date (DateTime — for Part 11), Reporter Name (Text), Severity (Picklist), Causality (Picklist), Outcome (Picklist), Is Expedited Report (Checkbox — triggers 15-day rule), Related Product (Lookup to Product), Related Study (Lookup to Study), Narrative (Long Text). Lifecycle: New → Under Assessment → Under Medical Review → Closed/Submitted to Regulator. Entry Action on "Submitted" state: set submission_date__c = NOW(), notify safety team. Validation Rules: prevent closing without narrative and causality assessment. Auto-number for case reference number.
Q101. What are the key differences between Vault Object-level and Vault Lifecycle-level state security?
Object-level security: Controls CRUD operations on the object record itself — who can create, read, edit, or delete any record of this object regardless of state. This is the broadest security layer. Lifecycle-level state security: Controls what actions (specifically state transitions) can be performed when the record is in a SPECIFIC state. A user may have Edit permission at the object level but the lifecycle might prevent them from transitioning to "Approved" state unless they have the "Quality Approver" role. Both layers must be aligned for a coherent security model.
Q102. How would you build a training tracking system using Vault Objects?
Objects: Training Item (curriculum, course, SOP) with fields: Title, Version, Effective Date, Training Type (Picklist). Training Assignment with Parent Lookup to Training Item and User Lookup to Assignee, plus fields: Assigned Date, Due Date, Assignment Status (Picklist). Training Completion (child of Assignment) with fields: Completion Date, Score, Completion Method, Verifier. Lifecycle on Assignment: Assigned → Completed → Verified → Expired. Validation Rule: Completion Date cannot be before Assigned Date. Entry Action on "Completed" state: send completion notification to the manager. Formula field on Training Item: "Completion Rate" = count of completed assignments / total assignments. This enables compliance training tracking and reporting.
